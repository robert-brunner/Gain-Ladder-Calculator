GAIN LADDER CALCULATOR — HELP

What this is

Live calculator for the binary-weighted resistor ladder gain-control network — a series resistor feeding a junction where five resistors can each be independently switched to ground. Whichever combination is grounded sets the divider ratio, which sets the gain. Also generates the firmware lookup table (tiltGainRange, 65 codes) mapped onto the closest achievable hardware state.

The circuit

IN drives the op-amp's + input. OUT feeds back into − and also drives R_SERIES down to a junction. Five resistors (R176, R171, R170, R169, R168) hang off that junction, each with a switch to ground. A resistor switched on contributes its conductance (1/R) to the parallel combination; switched off, it contributes nothing.

5 independent switches = 2⁵ = 32 possible combinations, each one discrete gain value. That's the hard ceiling on resolution — no firmware or math changes it, it's set by the resistor count.

The math

1/R_parallel = Σ (1/R_i) for every grounded resistor i
R_parallel   = 1 / (1/R_parallel)          [∞ if nothing is grounded]
Gain         = R_parallel / (R_SERIES + R_parallel)

Nominal gain   = midpoint of min & max achievable gain
Relative % = (Gain − Nominal) / Nominal × 100

All grounded → smallest R_parallel → minimum gain. All open → R_parallel = ∞ → maximum gain (1.0). Gain rises monotonically as fewer resistors are grounded, so the firmware table's nearest-match search can never produce an out-of-order jump — a correct search is mathematically incapable of that.

The firmware table (tiltGainRange)

The firmware expects 65 codes (decV −32…+32, hex 0x00–0x40). For each one, the tool computes the target gain (nominal × (1 + decV/100)) and searches all 32 achievable states for the closest match — reporting hardware state, actual %, and error in percentage points (pp).

Two different "error" numbers — don't mix them up

The tool reports linearity/error in two places measuring different things:

Full Sweep panel — raw achievable gain across the 32 physical codes (0–31) vs. a straight line from code 0 to code 31. Nothing to do with firmware. The gain formula is a divider, not linear in the switch bits, so this will always show real curvature (currently −9.32 pts at R_SERIES=1800Ω) — that's the network's inherent shape, not a bug.

Firmware Precision Table panel — each of the 65 decV targets vs. nearest achievable state, in relative %. This is the number that matters for firmware accuracy (currently +1.78 pp worst-case at R_SERIES=1800Ω).

These won't match each other — different axes, different reference lines, different code counts. If a number gets quoted, check which panel it came from.

Reading the error rate

65 requested firmware codes can't map onto 32 achievable states one-to-one:

  • Quantization (expected) — adjacent codes closer together than the real gain spacing land on the same state. Flagged with a faint highlight and a ↔ icon. Normal for a 5-bit network.
  • Coverage gap (a real design number) — if the achievable span is narrower than ±32%, the outer codes clamp to the best available end-state and error grows there. Watch "Achievable span" and "Worst-case error" in the Firmware Precision Table — both update live as resistor values change.

Using the panels

  1. Network Configuration — edit R_SERIES and the five resistor values. Toggle switches to explore any single state manually; the code slider steps through all 32.
  2. Full Sweep — all 32 raw states against an ideal straight line, for checking linearity independent of the firmware's specific 65-code target.
  3. Firmware Precision Table — matches the tiltGainRange array exactly, shows nearest-match hardware state, grounded resistors, and error for every one of the 65 codes.

Everything recomputes live. No reload, no recalculate button.
